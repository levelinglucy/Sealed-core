# Sealed-core development roadmap

**Current bounded step (draft only):** build and validate an opt-in, atomic core-side `NEW_TICKET` operation receipt in the same encrypted generation as ticket/metrics/intents. Acceptance: exact ID replay, mismatch rejection, legacy compatibility and interrupted precommit/committed tests. **Next** connect authenticated Gatekeeper reservation IDs and scope without broadening signed capabilities; only then design audited owner-local reconciliation. No automatic pending reset or merge.


**Current target:** [draft PR #8](https://github.com/levelinglucy/Sealed-core/pull/8) proposes a conservative response to missing Gatekeeper receipts after an interrupted local write. This is **not merged or released**. Previous concurrency and restore repairs remain integrated on main; protect data correctness before improving appearance or adding features.

1. **File restore staging (integrated candidate, complete):** PR #2 merged, exact main `385c4cd0`, 12/12 unit tests and all nine self-tests passed in CI. Verified missing/corrupt chunks preserve existing file contents; no stable tag was created.
2. **Directory restore rollback (integrated candidate, complete):** authenticate the entire archived object and extract into a safe, temporary sibling before any existing destination is moved. Keep old data recoverable through the publication step and on rollback failure. Eleven new synthetic cases cover corruption, invalid tar, path traversal, publish failure, rollback failure and normal restoration. [PR #4](https://github.com/levelinglucy/Sealed-core/pull/4) merged at `7e647ed0`; 23/23 unit tests and all 9/9 core self-tests passed in [PR CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42225523051) and [final main CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42225646052), each on Python 3.11/3.12. Crash gap and target-device uncertainties remain; this is not a stable release. Do not claim a stable release without platform evidence.
3. **Gatekeeper idempotency and scope (merged integrated candidate; PR #6):** reproducibly demonstrated duplicate same-key writes in baseline CI; added a cooperating-process request lock, three synthetic regression tests including external-acknowledger scope isolation. [Final PR CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42234685983) and [merged-main CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42234765405) passed 26/26 unittests and nine self-tests on each Python 3.11/3.12. This covers ordinary local concurrency, **not** crash-atomic exactly-once delivery.
4. **Crash-window fail-closed candidate (reviewable draft PR #8):** two synthetic interruption windows and pending-cache eviction were demonstrated by red CI on Python 3.11/3.12. A conservative pending reservation prevents a new signed same-key retry from blindly duplicating the mutation, but cannot determine whether it executed. Initial code checks passed 29/29 unit + nine self-tests per version; expanded tests including two real child-process exits passed [34/34 unit and nine core self-tests per Python version](https://github.com/levelinglucy/Sealed-core/actions/runs/42252218491) at `be1e8ae1` (before documentation update). Acceptance before any merge: complete validation at exact PR head; document and assess the operator reconciliation/rollback contract, including unavailable recovery UI; do not claim exactly-once delivery.
5. **Durable outcome and owner-only recovery research (in progress, draft only):** an additive encrypted opaque reservation ID and owner-local *read-only* pending inspector are now implemented as a preparatory slice, [verified in candidate CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42261063240), 38/38 unit plus nine self-tests on each Python 3.11/3.12. **They are not core-linked and cannot prove a commit.** Next evaluate a core-linked operation ID and atomic outcome receipt for one operation, including historic pending entries, safe scope association, deliberate owner-only resolution, source/state rollback and interrupted filesystem writes. Keep unknown outcomes blocked until evidence is sufficient. Keep draft changes isolated if reliable recovery cannot be supported. Revisit only on concrete evidence of a safe design.
6. **Target-device validation:** run synthetic smoke and recovery tests on trusted Pythonista/iPhone and applicable filesystems before claiming compatibility or stability.

Work in traceable topic branches. Record known limitations and checks with every merge. Preserve local-only operation, repository visibility, secrets, historical snapshots and recovery options.
