# Sealed-core developer notes

## Development summary

**Stage:** Gatekeeper crash-window fail-closed candidate on [draft PR #8](https://github.com/levelinglucy/Sealed-core/pull/8), **not merged or stable**; earlier concurrent-write and file/directory restore repairs integrated on main.
**Goal:** avoid blind duplicate effects when a signed keyed local write has no cached receipt following interruption.
**Latest:** a persisted `PENDING` reservation is created with the nonce *before* core execution. Matching signed retries receive `OPERATION_OUTCOME_UNKNOWN`; a completed receipt, including preexisting v2.2 records, still replays unchanged. Pruning preserves uncertain entries.
**Evidence:** three synthetic tests were first red on [baseline CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42242913268) (both Python 3.11 and 3.12); the initial repair passed 29/29 Python unit tests and 9/9 self-tests per Python version on [candidate CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42243006070). Expanded compatibility, capacity and two subprocess `os._exit` cases now pass [34/34 Python unit + 9/9 core self-tests per version](https://github.com/levelinglucy/Sealed-core/actions/runs/42252218491) on Python 3.11/3.12 at `be1e8ae1`. This tests process exit, not OS crash/power loss.
**Next:** design owner-local read-only pending inspection and an audited reconciliation protocol tied to a durable core operation ID; keep mutation/rollback out of scope until ambiguity is resolvable. Target-device checks still outstanding.
**Limits:** unknown result may mean no operation ran, or one committed. No safe automated reconciliation, no complete crash atomicity or indefinite completed-receipt retention; switching back to old code with pending entries may re-enable duplicates. All earlier directory power-loss and mobile constraints remain.

## Decision: add an atomic core-side NEW_TICKET receipt before Gatekeeper integration (2026-11-06; draft PR #8)

**Problem:** Gatekeeper has an encrypted PENDING ID, but a separate core commit is not linked to it. Matching ticket subjects or sender addresses are not proof of a particular signed request. Before wiring any recovery path, the core must be able to persist evidence in the *same transaction* as the side effect.

**Options:** maintain two state files and infer from timestamps (unsafe); store a separate core receipt after a ticket commit (still a crash gap); or add a minimal optional operation map in the existing encrypted core state generation (chosen). Old records load with an empty map. This does not alter existing `handle()` callers or open any listener.

**Implementation:** `handle_with_gatekeeper_operation(event, operation_id=..., request_hash=..., scope_id=...)` validates the 128-bit lowercase hex ID, 256-bit lowercase hex business hash and nonempty bounded scope. It enters the core store transaction, checks for existing exact-match ID evidence, calls existing `handle()` inside that transaction, and saves the exact returned ticket receipt alongside ticket, metric and intents before *one* encrypted state persist. A repeat of the same operation ID + request hash + scope returns the original receipt without another side effect; reusing an ID with different hash or scope fails. `get_gatekeeper_ticket_receipt(...)` provides read-only exact-match access; absence does **not** establish that a prior independent Gatekeeper request never ran. Operations grow with linked tickets and are not pruned while recoverability remains unresolved.

**Trust boundary and limits:** this core method is **not an authentication service** and trusts the future Gatekeeper call-site to derive request hash and scope from the verified signed principal/payload/idempotency key. It is currently NOT invoked from Gatekeeper, does NOT backfill earlier tickets, bind external ticket scopes, resolve PENDING reservations, or create a new signed API. File-backed transaction behavior is checked on Linux CI; no power-loss/device durability has been established. A previous core version will ignore the additive map, so downgrades while relying on it are unsafe. Review before connection and before considering merge.

**Acceptance plan:** isolated tests of exact replay, reject mismatched ID/hash/scope, ordinary legacy ticket compatibility, injected persist failure, and child-process `os._exit` before vs after encrypted commit. Next connect the actual encrypted reservation ID through verified Gatekeeper request handling and atomically associate scope at the core, then separately prove same-key signed retries can safely reconstruct receipts. Never auto-clear old/unlinked PENDING entries.

## Decision: fail closed on unreceipted idempotent writes (2026-11-06; draft PR #8)

**Evidence and prior behaviour:** On the already concurrency-locked main revision `6f6e9c67`, the nonce was persisted before execution, but the business idempotency key was only recorded *after* `core.handle`, scope binding and receipt storage. Two separate injected exceptions first proved the unsafe retry window: (a) after the core had committed `NEW_TICKET`, before `bind_ticket_scope`, leaving an orphan unscoped ticket; (b) after scope binding, before `record_idempotent_result`. In both cases the request returned `INTERNAL_ERROR` and a new valid signed nonce with the same key caused a second ticket to be created. A third baseline test proved that the cache-prune policy could discard a pending marker if one were introduced. Expected-red [CI run](https://github.com/levelinglucy/Sealed-core/actions/runs/42242913268) showed all three failures on Python 3.11 and 3.12. This is a local crash/fault window, not a remotely demonstrated exploit.

**Options considered:** (1) keep returning errors and document the race — no write protection; (2) infer completion by matching input payload to a ticket — unsafe because the core has no operation ID and identical payloads may be legitimate; (3) add an encrypted `PENDING` reservation in Gatekeeper state before mutation and deny automatic retries while outcome is unknown — small, conservative, but can strand keys; (4) move business operation, ticket scope and receipt into one audited core-linked encrypted transaction — stronger and recoverable, but requires a larger schema migration with crash tests. Chose (3) as a **reviewable draft**, not as a final exactly-once solution.

**Implementation:** `consume_nonce_and_check_idempotency` persists `PENDING` in the encrypted Gatekeeper store together with the nonce before returning to `_execute`. If an existing entry has a different business hash, key reuse is rejected as before. If it has a `result`, that exact cached response is returned as before (old records do not need a `status` field). If it lacks `result`, a matching newly signed retry receives `OPERATION_OUTCOME_UNKNOWN`, with no new mutation. Successful execution replaces the marker with a `COMMITTED` result. Retention prunes completed entries before uncertain ones; if all capacity is consumed by pending entries, new writes fail with `IDEMPOTENCY_CAPACITY_REACHED`. Existing receipts may still be evicted by the bounded cache and thus do **not** promise indefinitely repeatable results.

**Trade-offs:** fail closed has a real availability cost. Even a completely precommit failure after the reservation will remain pending; there is intentionally no reset, automated merge or inferred outcome. If a caller loses the original result and retries with a new key, duplication remains possible; human process must prevent it. The new stored fields fit the existing encrypted schema, but an older implementation silently ignores `PENDING`, making a naive code rollback dangerous. The code serializes cooperating local calls via the existing request lock, but independent direct-core writers can still bypass it. A file lock plus reservation is not crash-atomic across core and Gatekeeper, does not fix orphan scopes, and does not guarantee power-loss safety on unsupported filesystems.

**Acceptance:** synthetic `NEW_TICKET` operations with injected exceptions after the core commit and after ticket scope binding create one persistent ticket; distinct signed nonce retries with the same key fail closed; pending entries survive bounded pruning and capacity cannot silently discard them; historical completed receipts remain readable; ordinary sequential and parallel retries still work. No real data or remote network used. Keep in PR until review of unknown-result operational contract. Revisit for a core-linked operation ID/atomic write protocol and a safe owner-only reconciliation interface. See [recovery guide](./GATEKEEPER_RECOVERY.md) for explicit manual precautions.

## Decision: preparatory owner-local inspection, not automatic recovery (2026-11-06; draft PR #8)

**Problem:** Gatekeeper's encrypted PENDING reservations prevent blind retry but offer no safe owner-facing diagnostic or core-linked identifier. A matching ticket's fields do not prove it came from this write, and clearing a marker can duplicate a side effect. The encrypted Gatekeeper and core stores are separate commits.

**Alternatives:** (a) infer completion from ticket similarity or automatically reset older entries — rejected as unsound; (b) expose an owner-only signed API action — unnecessary new authorization surface; (c) add an encrypted opaque ID and local read-only inspector — chosen bounded step; (d) implement a durable core transaction ledger and audited reconcile/rollback — higher-value follow-up requiring broader tests and compatibility analysis.

**Implementation:** new pending records carry a random 128-bit hex correlation ID, preserved when a completed receipt is recorded. It is **not passed to or recorded by the core yet**. \`inspect_pending_local(storage_dir)\` requires the existing owner's environment secret and returns only an SHA-256 fingerprint of the compound business key, pending creation time, request hash, optional correlation ID and status. It acquires the cooperating request lock before reading under the state lock, so an ordinary in-progress request will finish first. No state mutation, new signed action, network endpoint, key/payload/nonce disclosure, auto reset, state schema migration or release. Historical pending entries return \`operation_id: None\`, and completed receipts remain invisible to the inspector.

**Trade-offs and acceptance:** operation IDs cost a small encrypted field per new reservation and cannot prove a commit; the hash of the key reference is for local matching, not authentication or anonymity. Synthetic tests verified stable pending identities across retry, unchanged encrypted bytes during inspection, redacted outputs, completed/legacy compatibility and no signed policy exposure: [candidate CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42261063240) passed **38/38 unit tests and nine core self-tests per Python 3.11 and 3.12**. This is a preparatory slice, not owner-controlled reconciliation. Next introduce an atomic core-side mapping from a reservation ID to its exact transaction receipt for one operation (likely ticket creation), then independently prove precommit/committed/retried behavior and scope handling before proposing controlled resolution. Preserve fail-closed semantics for other operations and interrupted filesystem writes.

## Decision: serialize Gatekeeper request transactions (2026-11-06)

**Observed defect:** `consume_nonce_and_check_idempotency` persisted the nonce and checked for an existing result, but the business operation and `record_idempotent_result` happened later and outside any shared execution lock. Two valid signed requests from the same principal, with identical action/payload/idempotency key and distinct nonces, could both pass the check before either result existed. Isolated test-only PR SHA `f063752b` reproduced **2 side effects rather than 1** on Python 3.11 and 3.12, while sequential replay and key-collision checks passed. This is a local API concurrency defect, not a verified remote exploit.

**Options:** (a) nonce lock alone — insufficient; (b) in-memory per-key mutex — insufficient across cooperating processes; (c) separate process-shared request lock across authentication, execution and result write — simple and fits existing `_StoreFileLock` cross-process convention; (d) durable transaction journal in the core store — better for recovery but a substantial, riskier schema/API change. Selected **(c)** for bounded repair and preserve (d) for a later milestone.

**Implementation:** `GatekeeperState.request_lock_path` is distinct from `.gatekeeper.lock`; the entire `GatekeeperV22.request()` normal path, including signed auth, nonce check, ticket-scope binding, local core operation and result persistence, runs under the new lock. State/Core locks remain separate inside. This also prevents a cooperating scoped read from overtaking an in-progress ticket creation. No encryption format, signature or role policy was changed; original historical files remain untouched.

**Acceptance:** independent Gatekeeper instances share a synthetic storage root; a deliberately delayed first write receives a parallel same-key retry; one operation executes and the other receives the identical cached result. Sequential same-key retry, payload mismatch, reused nonce, and different-scope `EXTERNAL_ACK` denial/own-scope success are covered. [Final merged-main CI](https://github.com/levelinglucy/Sealed-core/actions/runs/42234765405) passed 26 unit tests plus nine self-tests on both versions. This validates cooperating file-lock behavior on Linux runners, not crash recovery or all platforms.

**Remaining gap and revisit:** this is *not* a single crash-atomic transaction across two encrypted state files. A hard termination after `core.handle` but before scope binding or cached result persistence can leave an orphan scoped ticket or duplicate the action on a retry; even under the process-shared lock a fresh process cannot infer the missing receipt. Investigate a durable intent/commit marker or core-level transaction link with safe migration and crash injection before claiming exactly-once semantics. Non-cooperating direct core writers bypass the request lock. Reads serialize as a deliberate safety/throughput trade-off; revisit if profiling shows an actual bottleneck.

## Decision: stage and roll back directory restoration (2026-11-06)

**Before:** `restore_directory(overwrite=True)` removed the destination with `rmtree` / `unlink` before even decrypting the archive. A missing vault chunk, altered AES-GCM ciphertext, invalid tar, extraction error or interrupted write could therefore destroy the only available prior output.

**Alternatives:** (a) decrypt and extract directly into the old destination — no safe failure isolation; (b) make a full copied backup before in-place extraction — more I/O, still exposes partial new content; (c) stage the verified extracted directory beside the destination, rename old to backup, then rename new into place, with rollback — bounded memory, additional disk space, distinct rollback path. Selected (c).

**Implementation:** validate the original directory name; create owner-private temporary storage inside the target root; reuse vault chunk authentication and full SHA-256 verification for the archive; use `tarfile`'s data filter when supported and enforce a single expected top-level root. On older Python without the filter, reject archive links and special entries rather than allowing potentially unsafe extraction. Keep previous content in `.NAME.sealed-backup-UUID` outside the auto-removed staging directory. Restore it if the second rename fails, and leave it untouched if rollback itself fails. Delete the old backup only after publishing new data; preserve historical source files and the local-only design.

**Trade-offs:** requires approximately a second full plaintext archive plus extracted tree during staging; no long-term API/schema changes. There is a short gap between moving the old tree and making the new one visible. Abrupt termination, storage failure, or an uncooperative concurrent writer is not a guaranteed recoverable transaction. A crash can leave backup folders or plaintext staging; do not blindly delete them. Symlink-containing archives on old Python may no longer restore (security-first compatibility restriction). Directory data and permissions were not power-loss fsynced exhaustively; not certified on iPhone or non-POSIX filesystems.

**Acceptance:** missing/corrupt chunks, authenticated invalid tar and traversal attempts preserve old content; injected failed promotion rolls back; if rollback itself fails old data remains in a recoverable sibling; successful overwrite and fresh restores preserve bytes; standard smoke tests pass. Revisit if an audited portable crash-atomic directory exchange or a safe cross-platform exclusive publication mechanism becomes available.

## Decision: verify before publishing restored file (2026-11-06)

**Problem and evidence:** `_restore_vault_object_to_file` called `target.open("wb")` before verifying any chunk. On `overwrite=True`, that truncates an existing target; the exception handler then unlinks it after a missing or tampered chunk. This is a direct source-level data-loss risk, not a claim of remote exploitability. Existing tests covered successful unseal only.

**Alternatives:** (a) load whole content into memory before writing — simple, unacceptable for large backups; (b) stream to original destination and restore a backup on failure — more write cycles and complicated interruption recovery; (c) stream to a sibling staging file and publish only after integrity verification — bounded memory with ordinary filesystem atomicity.

**Choice:** (c). Use `NamedTemporaryFile(delete=False)` in the target directory with 0600 permissions and fsync after writing. Verify AES-GCM tags and the recorded full-object SHA-256 before publishing. For `overwrite=True`, `os.replace` atomically changes the directory entry on supported filesystems. For default non-overwrite, `os.link` creates the destination only if absent, avoiding a concurrent creator being replaced between precheck and publication. The temp inode is unlinked after success, and cleaned on ordinary exception. The key bytearray is zeroed in finally.

**Trade-offs and uncertainty:** This approach uses extra temporary disk space approximately equal to restored plaintext. A hard process crash can strand a mode-0600 plaintext `.sealed-*.tmp` file; the operator should inspect and remove these from the chosen output directory when recovering from a crash. Hard links are not supported by every filesystem, and a hard-link failure surfaces as an exception rather than falling back to a risky overwrite. Filesystem failures and host power loss are not comprehensively simulated. The original `overwrite=False` destination precheck is retained for a friendly error, but the hard-link operation supplies the race-safe final guard. This does not harden directory restore, which has its own destructive prevalidation path.

**Acceptance:** corruption or missing chunks leave existing target bytes unchanged; no partial new target appears; successful overwrite and fresh restores contain exactly original bytes; no staging files remain after ordinary success/failure; new tests and historical smoke tests pass on supported Python CI. Revisit if device support requires another exclusive publication mechanism or if crash-cleanup architecture is added.

## Architecture and trust boundary

The active imports are `sealed_core.py`, `gatekeeper_v2_2.py`, and `sealed_snapshot.py`; historical named files must not be silently rewritten. Local-only function calls are not proof of absence of application-level authorization defects. No network service was introduced in this change. Use synthetic data and temporary storage for tests; do not load user vaults or secrets as test fixtures.
